# 006 — Окно создалось ≠ человек его видит (кооперативная активация macOS 26)

**Дата:** 2026-07-27 · **Фаза:** релиз 1.0, финальный ребут-тест · **Нашёл:** человек, руками

## Что произошло

Финальная приёмка после перезагрузки. Человек кинул папку с mp3 в наблюдаемую папку и получил
ровно тот же симптом, с которого начиналась вся эпопея: **«ничего не произошло»**.

Разбор по unified log показал, что вся цепочка отработала идеально:

| время | что | кто |
|---|---|---|
| 20:57:13 | агент стартовал при загрузке | launchd |
| каждые 5 мин | тик по `StartInterval` | launchd |
| 21:13:32 | сработал `WatchPaths` на дропе | launchd |
| 21:13:45 | книга опознана, `open -b` → **rc=0**, в журнал `app_nudged` | агент |
| 21:13:45.891 | `runningboardd: Launch request … exPath:/Applications/mp3-to-m4b.app` (pid 2770) | LS |
| 21:13:46.343 | `[AppKit:AutomaticTermination] "No windows open yet"` | приложение |
| 21:13:46.4–.5 | **окно создано** (`window count = 1`) | приложение |
| 21:14:16 | App Nap включён — система считает приложение невидимым | система |
| 21:15:11 | человек кликнул сам → `occluded → visible`, первый за жизнь процесса Focal | человек |

Между 21:13:46 и 21:15:11 окно **существовало и было полностью перекрыто** чужим окном.
Восемьдесят пять секунд. Процесс всё это время был жив — «смерть через 30 секунд», которую я
сначала прочитал в логах, оказалась инвалидацией одной assertion при включении App Nap.

## Настоящая причина

macOS 26 (Tahoe) — **кооперативная активация**. У процесса, поднятого программно через
LaunchServices, нулевой «кредит активации», и WindowServer отказывает прямым текстом:

```
CPS: The requested process (pid = 2770) presents 0 windows … Denying the request.
CPS: Rejecting the request for pid 2770 due to the activation count being 0; … window count = 1.
```

Первый отказ — потому что LS-активация пришла раньше, чем окно создалось в
`applicationDidFinishLaunching`. Второй — уже при живом окне, на наш собственный вызов
`NSApp.activate(ignoringOtherApps: true)`. Deprecated-флаг `ignoringOtherApps` на Tahoe — **no-op**.

Итог: `makeKeyAndOrderFront` упорядочил окно, но позади фокусного приложения, и приложение не
получило права выйти вперёд.

## Почему это не поймали

Три «зелёных», каждый из которых честен по отдельности и все вместе не значат ничего:

1. `open -b` вернул **rc=0** — LaunchServices приняла запрос. Про фокус она не утверждала.
2. Агент записал `app_nudged` — правдиво: он нуджил.
3. Приложение вызвало `makeKeyAndOrderFront` + `activate` — вызвало, да. Результат не проверял.

Это тот же класс, что и «тихие зелёные» из M1–M6, только на новой территории: **проверялся факт
вызова, а не факт эффекта**. Вся цепочка рапортовала успех, а человек смотрел на пустой экран.

Плюс моя собственная ошибка. В `arch/raise-app-claude.md` я записал допущение:

> «На НЕзапущенное — холодный старт… **В приложении менять нечего**»

Оно писалось до того, как я узнал про кооперативную активацию, и закрыло приложение от подозрений
на весь цикл. Диагноз потом пришлось искать в логах, а не в коде, — и первая моя гипотеза
(«полная переустановка при старте блокирует окно») тоже оказалась неверной: окно рождалось за 0.6 с.

## Правило на будущее

1. **`rc=0` внешней команды — не доказательство эффекта.** `open`, `launchctl`, `osascript`
   отвечают «запрос принят». Между «принят» и «человек увидел» стоит политика ОС, которая может
   отказать молча. Такой вызов сам по себе никогда не закрывает задачу.
2. **Видимость проверяется у того, кто её знает.** `occlusionState` окна знает только само
   приложение. Кто нуджит снаружи (агент), тот принципиально не может подтвердить показ — и не
   должен делать вид, что может. Не заводи ради этого канал обратной связи: перенеси проверку
   туда, где есть факт.
3. **У «показать окно» обязана быть лестница эскалации с проверкой на каждой ступени.**
   Упорядочить → проверить видимость по таймеру → `orderFrontRegardless()` → разовый
   `requestUserAttention`. Одна ступень «вызвал и надеюсь» — это не показ окна.
4. **Гарантированный фокус без действия человека на Tahoe недостижим** — это политика ОС, а не
   наш баг. Цель формулируется как «окно видимо и не перекрыто», а не «окно перехватило клавиатуру».
   Требование к продукту надо писать в достижимых терминах, иначе будешь чинить погоду.
5. **Допущение «здесь менять нечего» в арх-документе — обязано быть помечено как допущение**, с
   датой и основанием. Иначе оно читается следующим циклом как проверенный факт и выводит целый
   слой системы из-под подозрения. Моё стоило одного полного ребут-теста человека.
6. **Приёмка сценария — только глазами на экране.** Ни один лог не заменяет ответ на вопрос
   «человек увидел окно?». Сценарий, конечная точка которого — восприятие человека, закрывается
   человеком, а не строчкой в журнале.

## ⚠️ Ловушка для того, кто будет разбирать СЛЕДУЮЩИЙ инцидент

Лестница зовёт `NSApp.activate()` на каждом входе, включая повторные. На Tahoe каждый такой вызов
оставляет в unified log строку `CPS: Rejecting the request … activation count being 0`. **Это
ожидаемое поведение, а не признак поломки** — именно по этим строкам ставился диагноз выше, и
серия отказов при следующем разборе легко читается как «лестница не работает».

Признак того, что лестница ОТРАБОТАЛА, — не отсутствие отказов активации, а то, что окно стало
видимым: переход `occluded → visible` у окна либо `orderFrontRegardless` в трассе. Отказ активации
и видимость окна — независимые вещи, в этом вся суть фикса.

- `app/WindowPresentation.swift` — чистый решатель лестницы (покрыт автотестом);
- `presentWindow()` как единственная точка показа, `NSApp.activate()` вместо deprecated;
- самопроверка видимости по `occlusionState` с эскалацией `orderFrontRegardless` → dock bounce;
- тёплый путь `bringWindowForward()` **удалён** (не обёрнут) — все пути показа идут через

- +62 юнит-проверки правила лестницы, проверенные мутациями (6 внесённых дефектов пойманы,
  2 подстройки констант — нет, значит тест привязан к смыслу, а не к литералам);
- допущение в `arch/raise-app-claude.md` помечено как опровергнутое.
