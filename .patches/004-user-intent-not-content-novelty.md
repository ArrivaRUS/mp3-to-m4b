# 004 — Намерение пользователя ≠ новизна контента (триггер = действие, не «новая книга»)

**Когда:** 2026-07-07, фикс «дроп папки → приложение само всплывает». Человек оспорил моё (и архитекторское) требование к «новизне».

## Что случилось
Спроектировал побудку приложения так, что она срабатывала только на **content-новую** книгу (которой раньше не было). Человек возразил: «если пользователь СОЗНАТЕЛЬНО кладёт папку в папку конвертации — он хочет её конвертнуть, не важно, собиралась ли она раньше; окно обязано всплыть». Он прав: повторный дроп уже-собранной книги дедупался как `done` и молчал.

## Причины
- **Конфляция двух разных вещей:** «не всплывать САМОПРОИЗВОЛЬНО» (рестарт агента при логине, петли на своих же командах, прогресс-тики) и «не всплывать на ДЕЙСТВИЕ пользователя». Первое надо подавлять, второе — никогда. Я привязал подавление к новизне КОНТЕНТА, а надо было — к самопроизвольности СОБЫТИЯ.
- Дедуп по content-rev (relpath+size+mtime) слеп к повторному дропу: Finder сохраняет mtime при копировании → тот же rev → «ничего не изменилось».

## Как починили (двойной архитектор)
Триггер = **событие дропа**, не новизна. Два сигнала «сознательный (пере)дроп»:
- **inode+st_dev в source_rev** — копия папки = физически новые файлы = новые inode → rev меняется → ре-арм. (Claude #1)
- **presence-ledger «был → исчез → появился»** — Finder MOVE в пределах тома СОХРАНЯЕТ inode, а drag на Desktop часто именно move; inode это пропустит → нужен трек присутствия. (Поймал Codex #2 — ровно катастрофа-в-миниатюре, ради которой держим второго архитектора на другой LLM.)
- **Миграция-гард** старых манифестов (rev без inode) — тихий апгрейд без шторма окон при обновлении.

## Правило на будущее
- **Действие пользователя = намерение. Никогда не гейти его на «новизну».** Пользователь положил файл/папку/нажал — обслужи. «Дедуп по контенту» уместен, чтобы не пересобирать молча тождественный выход, но НЕ чтобы проглотить сознательный жест.
- **Разделяй «самопроизвольное» и «пользовательское».** Подавляй спам от рестартов/петель/тиков — по стабильному baseline (что уже показано). НО любой свежий пользовательский ввод пробивает подавление.
- **«Пользователь положил папку» на macOS = либо copy (новые inode), либо move (тот же inode).** Одного inode мало — Finder drag в пределах тома это move. Нужен И content-rev с inode, И presence-трек. Проверяй эмпирически: `cp` даёт новый inode, `mv` сохраняет (подтверждено на реальном APFS/iCloud-Desktop).
- **Когда человек оспаривает требование — часто он прав про НАМЕРЕНИЕ, а не про механизм.** Слушай про «зачем пользователь это делает», переспроектируй триггер, потом уже механизм. Второй архитектор на другой LLM ловит краевые случаи (здесь — move-in), которые первый пометил как «P2, потом».
