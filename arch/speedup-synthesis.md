## ✅ РЕШЕНИЕ ЧЕЛОВЕКА (2026-06-30) — два режима, выбор в UI
Вместо одного компромисса — **тумблер режима сборки в окне подтверждения**:
- **«Быстрый режим»** — распараллеливание процессов (параллельные группы глав → concat `-c copy`), ×6–10; возможны паузы ~25 мс на границах глав. Default (приложение про аудиокниги-речь, где это неслышно).
- **«Бесшовный режим»** — битовая точность на стыках глав (single-pass энкод), медленнее (~×1.2–2.35 на `aac_at`).
Оба пути реализуются; `aac_at` + прогресс-бар — общий бесшовный фундамент (Ступень 1). `build()` выбирает путь по `params.build_mode` (`fast`/`seamless`). Параметр едет в манифест (DEFAULT_PARAMS) и в `confirm-build`. Подробности плана — ниже (Ступень 2 = «Быстрый», Ступень 1/fallback = «Бесшовный»).

## Диагноз (обе головы согласны, высокая уверенность)
- Узкое место — серийный AAC-энкод ОДНИМ процессом ffmpeg на ~1 ядро.
- `-threads` аудио НЕ параллелит (#1 ЗАМЕРИЛ: 12.77 vs 12.83 c). Ускорение — только параллельные ПРОЦЕССЫ.
- m4b = AAC в MP4 → ре-энкод mp3→AAC неизбежен; выигрыш — за счёт времени энкода (`aac_at`) и параллелизма, а склейку делаем stream-copy (`-c copy`, без ре-энкода).

## Где головы сошлись
1. **`aac_at` (Apple AudioToolbox)** — бесплатный безрисковый шаг: смена энкодера в текущем single-пути, бесшовность цела. #1 замер ×1.24; #2 оценка 1.3–3×. **CBR 192k** (VBR ломает оценку размера для disk-гейта и окна). Fallback на встроенный `aac`, если `aac_at` недоступен.
2. **Параллелизм — главный выигрыш** (×6–10 на длинной книге) через пул ПРОЦЕССОВ.
3. **Бесшовность — центральный риск.** Независимо кодированные куски несут AAC priming/delay → ~23 мс тишины на КАЖДОМ стыке. #1 ДОКАЗАЛ `silencedetect`: ровно на 180/360/540/720 c.
4. **Метки глав — из ИЗМЕРЕННОЙ (ffprobe) длительности кусков, НЕ из исходных mp3** — иначе дрейф (#1: до ~1.3 c на 56 глав). Обязательный assert в тест-плане.
5. Промежуточный контейнер — **.m4a/mp4** (хранит timing/edit-list), НЕ ADTS `.aac`.
6. Диск пик ≈ 2× финал → поднять free-space-гейт (#2: ×2.1–2.4).
7. Групповая отмена ВСЕХ детей (SIGTERM→грейс→SIGKILL, reap всех); прогресс — в ТОТ ЖЕ контракт state.json (UI не меняется).
8. `out_time_ms` в ffmpeg-`-progress` исторически в МИКРОсекундах — брать `out_time_us`/1e6.

## Ключевой синтез (где #2 улучшает #1)
#1 анализировал per-chapter «в лоб» → **55 швов** на 56 глав. #2 предложил **параллельные ГРУППЫ подряд-идущих глав (K≈workers)**: внутри группы главы кодируются ОДНИМ непрерывным проходом (стыки внутри группы бесшовны), швы только МЕЖДУ группами = **workers−1** (напр. 7 при 8 воркерах), и эти швы попадают РОВНО на границы глав = естественные паузы.

Итог: почти та же скорость, что per-chapter, но швов **7, а не 55**, и все — в паузах между главами. Строго лучше. #1 эмпирически обосновал (23 мс шов + дрейф 1.3 c) структурную идею #2 — ровно тот случай, ради которого нужны две головы.

## Рекомендация Юрки — двухступенчато
**Ступень 1 (внедряю в следующем батче БЕЗ отдельного решения — бесплатно/безопасно):**
`aac_at` CBR 192k (fallback `aac`) + прогресс-бар/отмена (батч-4 СЛИВАЕТСЯ сюда — тот же single-пасс `build_m4b`). Бесшовно. Выигрыш скромный (~×1.2–1.3) + честный прогресс.

**Ступень 2 (после ⛔ go человека на компромисс):**
параллельные ГРУППЫ глав → concat `-c copy`. ×6–10. Защиты: главы из probed-длительности; .m4a-промежутки; 2× disk-гейт; групповая отмена; прогресс = группы/главы done; QA на швы (`silencedetect` на границах групп) + fallback на single-encode при провале валидации/дрейфа.

**Fallback, если нужна бит-в-бит бесшовность:** `aac_at` VBR single-pass (×2.35, без параллели), но размер файла менее предсказуем.

## ⛔ Решение человека (СТОП)
Параллель даёт ×6–10, но добавляет ~23 мс тишины на границах глав (естественные паузы; для речи практически неразличимо; слышно было бы только на музыке). Принять ради скорости? Альтернатива — бескомпромиссная бесшовность (`aac_at` VBR ×2.35).

## Порядок (по зависимостям, overlap по `build_m4b.py`)
Батч 1-3 (SR/нарезка/подпись — в работе) → **Батч 4 = прогресс+отмена+Ступень 1 (`aac_at`)** одним dev (single-пасс) → [по go] **Ступень 2 (параллель)** — отдельный dev, переписывает прогресс-ВЫЧИСЛЕНИЕ под группы (UI/контракт не трогая) → QA швов на реальной многоглавой книге.

## Компоненты (свод обоих, для будущего dev — изменения в `build_m4b.py`)
- `_encoder()` — детект `aac_at` (кэш на процесс), fallback `aac`.
- `_audio_encoder_args(params, encoder)` — argv энкодера: `aac_at -aac_at_mode cbr` / `aac`, битрейт/SR/каналы.
- `_run_ffmpeg_progress(argv, …, total_ms, cb)` — парс `-progress pipe:1` (`out_time_us`).
- `_plan_encode_groups(chapters, sources, workers)` — баланс глав в K≈workers групп по `duration_ms`.
- `_build_with_parallel_groups(...)` — пул Popen, энкод групп→.m4a, probe длительностей, concat-demuxer `-c copy` + главы (`-map_chapters 1`) + обложка + faststart.
- `_chapter_marks(probed_durations)` — START/END из ИЗМЕРЕННЫХ длительностей (assert: END[-1]==probed_total ±1 фрейм).
- `_terminate_ffmpeg_many(children)` — гасит ВСЕХ детей; `_cleanup_temp_tree` — `shutil.rmtree` скрытой temp-ДИРЕКТОРИИ `.<name>.<token>.chunks/`.
- `_ensure_free_space(..., strategy)` — множитель ~2× на параллель-пути.
- `build(manifest, out_path=None, progress_cb=None)` — выбор стратегии: 1 глава → single; parallel && ≥2 глав → groups; иначе текущий путь.
