# План: ранний нудж (D17) — окно до чтения метаданных

**Архитектор #1 (Claude) · 2026-07-28 · вход: decisions/log.md D16/D17, agent/scan.py, agent/dispatcher.py, agent/cover.py, agent/build_m4b.py, app/main.swift, app/StateModel.swift, замеры из брифа**

Несущая идея: **время до окна перестаёт зависеть от сети и от объёма книги**.
Достигается не «ускорением скана», а сменой протокола: манифест становится
**монотонно дозаполняемым документом** с явной фазой полноты, а нудж уезжает в
самое начало конвейера. Сеть (веб-обложки) вообще уходит с критического пути —
и окна, и кнопки «Собрать», и старта сборки.

## 1. Целевая картина

Дроп папки «Толстой - Война и мир» (56 mp3, 1.3 ГБ) при уже скопированных файлах:

| t (≈) | агент | человек видит |
|---|---|---|
| 0.0 c | launchd будит агента (WatchPaths) | — |
| 0.25 c | старт+импорты; access-гейт ok; rev-проверка (stat-only) — книга новая | — |
| 0.25–0.76 c | **дебаунс E10** (`_files_are_stable`, 0.5 c) — файлы не растут | — |
| ~0.78 c | **СКЕЛЕТ**: манифест `phase=skeleton` (token+rev отчеканены), публикация #1, **нудж** | — |
| ~1.2 c | (агент пробит 56 файлов, 0.25 c) | **окно открылось**: имя книги и автор из имени папки, список из 56 глав по именам файлов, «56 файлов · 1.3 ГБ», параметры качества активны; длительности `–:––`, обложка-плейсхолдер, «Собрать» неактивна с подписью-причиной |
| ~1.3 c | **ГЛАВЫ**: `phase=chapters` (ID3-имена/порядок/длительности, автор/название из тегов, `source_samplerate`, встроенная обложка), публикация #2 | длительности глав и общая длительность заполнились; заголовок/автор уточнились (если человек их не трогал); у книги со встроенной обложкой — обложка на месте и **«Собрать» активна** (phase=ready уже здесь) |
| ~2.4 c | **ГОТОВО ЛОКАЛЬНО**: `phase=ready` (сгенерированные варианты обложки, дефолт выбран), публикация #3 | лента обложек: [из файла][варианты 1..N] + хвостовой слот «ищу в сети…»; **«Собрать» активна** |
| после drain | **ВЕБ**: `phase=done` (веб-кандидаты дописаны В КОНЕЦ ленты; сеть мертва → просто done), публикация #4 | хвостовой слот исчез: либо +N плиток «из сети», либо тихо ничего — ждать больше нечего |

Клик «Собрать» возможен с ~1.3–2.4 c и **не ждёт веба**: порядок процесса
становится `recover → scan(скелет→главы→ready, только локальное) → drain(сборка) →
web-обогащение → exit`. Мёртвая сеть (2×6 c таймаутов) теперь стоит ноль секунд
и окну, и сборке — она тратится после них, в хвосте процесса.

Пол: ~0.8 c до нуджа (0.25 старта + 0.51 дебаунса + ~0.02 обход/запись/exec) —
совпадает с полом из брифа. Дебаунс НЕ трогаем: это семантика E10, а не жир.

## 2. Протокол манифеста (ядро)

### 2.1. Одно новое поле

```json
"phase": "skeleton" | "chapters" | "ready" | "done"
```

- **Монотонная лестница**, только вверх. Пишет ТОЛЬКО агент (writer не меняется),
  каждая ступень — один атомарный `write_json_atomic` (tmp→rename), поэтому
  читатель в любой момент видит целостный манифест какой-то одной фазы.
- **Отсутствие поля = `done`** (legacy-манифесты писались одним выстрелом и
  всегда полные). Совместимость со старыми книгами автоматическая.
- Поле осмысленно только при `status == "pending-confirm"`. После confirm/skip
  оно замораживается и никем не читается (сборка живёт на `status`).
- Один bool (`metadata_complete`) отвергнут: он не отличает «обложки ещё ищутся»
  от «искать больше нечего», а UI обязан честно показать момент «ждать нечего».

### 2.2. Состав по фазам (что уже есть, что добавляется)

| поле | skeleton | chapters | ready | done |
|---|---|---|---|---|
| `book_id`, `src_dir`, `status=pending-confirm` | ✅ | = | = | = |
| `source_rev` (v2, stat-only — «бесплатная» идентичность), `source_rev_v` | ✅ | = | = | = |
| **`confirm_token`** | ✅ **чеканится здесь, один раз** | = (никогда не перечеканивается) | = | = |
| `processed_keys` | `[]` | сохраняется | = | = |
| `params` | `DEFAULT_PARAMS` (финальные — фазы их не трогают) | = | = | = |
| `title`/`author` | из имени папки (`parse_author_title_from_folder`, чистые строки, 0 мс) | из ID3 (перезапись) | = | = |
| `chapters[]` | из имён файлов: `index`, `file`, `name` = cleaned filename, `duration_ms: null`; порядок — natural sort | из проб: ID3-имена, длительности, порядок по track-тегам | = | = |
| `total_size_bytes` (нов., опц.) | ✅ из тех же stat | = | = | = |
| `total_duration_ms`, `source_samplerate` | отсутствуют | ✅ | = | = |
| `cover_state`/`cover_preview` (embedded) | отсутствуют | ✅ (extract 0.03 c) | = | = |
| `cover_options`/`cover_selected` | отсутствуют | только embedded, если есть | + generated, дефолт выбран | + web (ДОПИСАНЫ В КОНЕЦ) |
| `phase` | `"skeleton"` | `"chapters"` — или сразу `"ready"`, если есть embedded (гарантия обложки уже выполнена) | `"ready"` | `"done"` |

Ключевой трюк скелета: он **не пустой**. Имена файлов, их число, размер и
разбор имени папки доступны даром (тот же stat-проход, что и `source_rev_for`),
и это ровно те же fallback-значения, которые финальный манифест использует при
отсутствии ID3 (`chapter_name` → cleaned filename; автор/название → имя папки).
Скелет — не «спиннер вместо данных», а честное приближение снизу.

### 2.3. Кто когда пишет и публикует

`run_scan` (внутри одного процесса, как сегодня):

1. **Проход 1 — скелеты.** Для каждой подпапки: `source_rev_for` (только stat) →
   **если rev не изменился И `phase ∈ {ready, done, отсутствует}` — вернуть манифест
   как есть** (сегодняшнее короткое замыкание `_write_manifest`, к нему добавлено
   условие фазы — см. resume в 2.4) → иначе дебаунс E10 → записать скелет.
   Группа loose-mp3 проецируется как сегодня (в её пути нет сети — ранний скелет
   ей не нужен). Затем `_publish_showcase_and_maybe_open` — **публикация #1,
   единственный нудж** (ключ `book:<id>:<rev16>:<token16>` уже полный — token из скелета).
2. **Проход 2 — главы.** Для каждой книги с `phase < chapters`: `_probe_book`
   (параллельный, как есть) → `order_chapters` → главы/теги/длительности/`source_samplerate`
   → извлечь embedded → атомарная перезапись с **сохранением** token/rev/`processed_keys`/params.
   Публикация #2 через ту же `_publish_showcase_and_maybe_open` — ключи не изменились
   ⇒ нуджа нет по построению.
3. **Проход 3 — локальные обложки.** `generate_variants` (Pillow, ~1.1 c) →
   `cover_options` += generated, `cover_selected` = embedded||gen-0 → `phase=ready`.
   Публикация #3, снова без нуджа.

`__main__` (порядок фаз процесса меняется — это второе несущее решение):

4. `drain_commands()` — как сегодня. К этому моменту всё pending уже `ready`
   ⇒ подтверждение, пришедшее «пока искали обложки», строит книгу БЕЗ ожидания веба.
5. **Новый проход `enrich_web_covers()`** (после drain, до exit): для каждого
   манифеста `status==pending-confirm && phase==ready` при включённом вебе —
   `search_web` → веб-опции **дописываются в конец** `cover_options` (см. §7 Q1),
   `cover_selected` не трогается (дефолт и так никогда не был веб-опцией) →
   `phase=done`. Веб выключен/пусто/сеть мертва → просто `phase=done`.
   Одна публикация в конце прохода (стиль `refresh_showcase` — без нуджа).
   Книги, ушедшие из pending (converting/done/skipped), не трогаются.
   Между книгами — проверка `shutdown.requested()`.

`refresh_showcase` не меняется: он проецирует манифесты как есть; строка
showcase дополнительно несёт `phase` (см. 2.5).

Заметка о жизни «застрявшего ready» (сборка отменена, веб-проход её книгу
пропустил, т.к. она была converting): следующий же запуск агента — а удаление
файла cancel-команды само дёргает WatchPaths — доводит её до `done`. Система
самозалечивается за один тик.

### 2.4. Resume после падения (обязательная часть протокола)

Процесс может умереть между фазами (kill, ребут). Тогда на диске лежит валидный
манифест `phase=skeleton|chapters`, а `source_rev` у него уже **финальный**
(stat-based формула одна). Поэтому короткое замыкание «rev не изменился» обязано
смотреть и на фазу: `rev совпал && phase ∈ {ready,done,∅}` → как есть;
`rev совпал && phase ∈ {skeleton,chapters}` → **достроить фазы с текущей ступени,
сохранив `confirm_token`/`processed_keys`** (не перечеканивать!). Нудж при resume:
если публикация #1 успела — ключ уже в notified-леджере, повторного нуджа нет;
если не успела — нудж честно случится впервые. В обоих случаях суммарно один.
Без условия фазы в коротком замыкании скелет застревал бы навсегда — это
главная дыра наивной реализации, и она закрыта на уровне протокола.

### 2.5. Читатели

- **`dispatcher.validate_command`** — новый шаг после проверки статуса:
  `manifest_build_ready(manifest)` (единственная функция-определение готовности:
  `phase ∈ {ready, done, отсутствует}` **И** `chapters` непуст **И** ≥1 глава с
  `duration_ms > 0`). Не готов → `VERDICT_REJECT`, причина
  `manifest_not_ready:<phase>`, событие `confirm_rejected_not_ready`, команда
  удаляется, книга остаётся pending. (Не «отложить»: команда против скелета —
  это всегда баг клиента или гонка миллисекунд; в нашем же процессе drain идёт
  ПОСЛЕ ready, так что честный клиент сюда не попадает.)
- **`build_m4b`** — третий эшелон уже существует: пустые/безразмерные главы →
  `BuildError("no_usable_chapters")` (build_m4b.py:1936). Фиксируем регресс-тестом.
- **Приложение** (`StateModel.BookManifest`): декодирует `phase` (отсутствие →
  `.done`), `isBuildReady` — зеркало `manifest_build_ready`. Строка showcase несёт
  `phase`, чтобы очередь могла показать «читаю…» без чтения манифеста.

### 2.6. Окно: рендер по фазам и правила слияния (app)

Рендер — «контент-первый» (что есть в манифесте, то и показано), фаза управляет
только плейсхолдерами и кнопкой:

- **skeleton:** заголовок/автор из папки (поля редактируемы сразу), список глав
  из имён файлов (строки некликабельны — это дисплей), в колонке длительностей
  `–:––` тусклым **фиксированной ширины** (без сдвига вёрстки), метабар
  «56 файлов · 1.3 ГБ · длительность считается…», квадрат обложки — нейтральный
  плейсхолдер с мягкой пульсацией (не спиннер и не «ошибка»), оценка размера «—»,
  «Собрать» disabled с подписью «Читаю метаданные…». Высота окна уже финальная
  (список глав полный) — окно не прыгает.
- **chapters:** длительности вписываются на свои места; заголовок/автор
  обновляются ТОЛЬКО если поле pristine; одноразовая коррекция порядка глав, если
  ID3-треки не совпали с natural-sort (без анимации, строки keyed by `file`).
- **ready:** лента обложек появляется/дополняется строго append-only; дефолт
  подсвечен; «Собрать» становится активной **один раз** (фаза монотонна ⇒ мигание
  disabled↔enabled исключено по построению); хвостовой слот «ищу в сети…» виден
  только пока `phase==ready` и веб включён.
- **done:** хвостовой слот исчезает; если веб ничего не дал — тихо (лента уже
  полна локальными вариантами; отсутствие «из сети» не преподносится как ошибка).

Деградация: сеть умерла — окно давно открыто и полнофункционально; человек
узнаёт «ждать больше нечего» по исчезновению хвостового слота (phase=done
приходит после таймаутов, ≤ ~13 c). Никаких красных состояний: веб — бонус.

Слияние при обновлении манифеста — чистая функция (тестируемая, как
`WindowPresentation`): `merge(old, new, dirtyFields) -> viewState`. Это самое
ковкое место app-части: `@State` в `ConfirmView` сеется в init и сам по себе
НЕ обновится при перезаписи манифеста — нужен явный onChange + merge:

| поле | человек не трогал | человек трогал |
|---|---|---|
| title/author | обновить из манифеста | оставить его текст навсегда |
| выбор обложки | следовать `cover_selected` | оставить его выбор |
| params (битрейт и пр.) | фазы их не меняют — конфликтов нет | его значения |
| главы | заменить целиком (append/уточнение) | нередактируемы |

`sent`/`skipSent`-локи и лестница показа окна (D16, свежий фикс в
`WindowPresentation`/`selfcheck_routing`) не трогаются. Закрыл окно / нажал
«Пропустить» во время дозаполнения: команды дренятся после ready (тот же
процесс), skip штатно бьёт по live-манифесту; `enrich_web_covers` пропускает
не-pending; повторного подъёма окна нет (ключ уже в notified-леджере).

Совместимость версий: новый app + старый агент → манифесты без `phase` =
`done` → поведение сегодняшнее. Старый app + новый агент → скелет отрендерится
(поля декодируются терпимо, `duration_ms:null` app уже умеет), «Собрать» без
гейта — но агентский гейт I-E1 отбивает команду; окно догонит по file-watch.
Staged-агент автообновляется приложением при первом запуске — окно рассинхрона
минуты, данные защищены.

## 3. Инварианты и чем каждый проверяется

Новая сьюта `agent/selfcheck_early.py` (§early), подключается в `selfcheck_all`
плоско. Тестовые швы: `MP3TOM4B_HALT_AFTER_PHASE=skeleton|chapters|ready`
(run_scan возвращается после публикации этой фазы) + существующие
`MP3TOM4B_NUDGE_CMD` (рекордер) и `MP3TOM4B_COVER_WEB`.

| # | инвариант | проверка |
|---|---|---|
| I-E1 | **Fail-closed сборка**: нет `build_started` для манифеста, где `manifest_build_ready()==False` | §early: halt после skeleton → руками положить confirm-build с валидными token/rev → drain → есть `confirm_rejected_not_ready`, нет `build_started`, нет `.m4b`, книга pending. Бэкстоп: прямой вызов `_real_build` на скелете → манифест в `error: no_usable_chapters`, файла нет |
| I-E2 | **Один нудж на цикл книги**; token скелета неизменен до done | §early: полный прогон новой книги → рекордер вызван ровно 1 раз; token, прочитанный на каждом halt-шве, идентичен; в notified.json один ключ. §nudge: все существующие проверки остаются зелёными без правки ожиданий |
| I-E3 | **Дебаунс раньше нуджа**: нестабильные файлы → ни скелета, ни нуджа | §early: копия «в полёте» (растущий файл) → `book_still_copying`, манифеста НЕТ на диске, рекордер молчит; после стабилизации — один нудж |
| I-E4 | **skip/done/unchanged**: rev совпал и фаза терминальна → ноль записей, ноль нуджей | §early + §skip: rescan skipped/done книги → mtime манифеста не изменился, нет `manifest_phase`-событий, рекордер молчит |
| I-E5 | **Resume**: смерть между фазами достраивается с тем же token, суммарно ≤1 нудж | §early (halt-шов) + §reliability (реальный SIGKILL между фазами): relaunch → phase=done, token тот же, рекордер суммарно 1 раз |
| I-E6 | **Веб не блокирует**: drain раньше веб-прохода; run_scan не ходит в сеть | §early: подложенный заранее confirm → в журнале `build_started` раньше веб-событий; при `MP3TOM4B_COVER_WEB=0` phase=done без сетевых обращений |
| I-E7 | **Legacy**: манифест без `phase` строится как раньше | §early: старый манифест → confirm → `build_done` |
| I-E8 | **Целостность фаз**: на каждом шве на диске валидный манифест своей фазы (token/rev/status на месте) | §early: schema-assert манифеста на каждом halt; refresh_showcase поверх скелета → строка с честным счётчиком глав, без падений и нуджей |
| I-E9 | **Один нудж на публикацию** при N новых книгах (rapid-fire) | §nudge rapid-fire остаётся зелёным (публикация #1 общая для всех скелетов) |
| I-E10 | **UI не мигает**: гейт кнопки монотонен; merge-правила по матрице pristine/dirty | Swift-юниты в стиле `selfcheck_routing.swift` на чистые функции `isBuildReady`/`merge` |
| I-E11 | **Reconvert = один выстрел**: force-путь пишет сразу полный манифест (`phase=done`), новый token, один нудж | §reconvert: + assert `phase=="done"` у переармированного манифеста (остальное уже проверяется) |

Плюс: полный гейт 21/21 обязан остаться зелёным; latency-sanity (нудж < 2.5 c
при выключенном вебе) — одна нестрогая проверка с щедрым порогом; основные
утверждения — порядковые (по журналу событий), не по секундомеру.

Новое событие журнала: `manifest_phase {book_id, phase}` на каждой ступени —
это то, на чём держатся порядковые проверки.

ожидания порядка) + §nudge/§skip/§reconvert/§reliability.

**M-C. Приложение** — параллельно M-B (зависит только от спеки поля из M-A) — ~1 день.
`StateModel`: `phase`/`isBuildReady`/`totalSizeBytes`; `main.swift ConfirmView`:
рендер фаз (плейсхолдеры, фиксированные ширины длительностей, хвостовой слот
ленты), чистая merge-функция + подключение через onChange, гейт кнопки;
`QueueView`: подпись «читаю…» для skeleton-строк. Лестницу D16 не трогать.
Гейт: Swift-юниты (I-E10) + сборка.

**M-D. Свод и живой прогон** — после M-B и M-C — ~0.5 дня.
`selfcheck_early` в `selfcheck_all` (плоско, без вложенных прогонов),
test-plan.md, docs; живой тест уровня «ребут-тест №3»: реальный дроп
56-файловой книги, замер дроп→окно и дроп→активная «Собрать» при живой и
убитой сети; урок в `.patches/` при любых расхождениях. Финальный GREEN —
визуальная сверка Юрки по чеклисту фаз §2.6.

Параллелить можно только M-B ∥ M-C. M-A — строго первым: он фиксирует спеку
поля, от которой зависят оба.

## 5. Как закрыт каждый риск брифа

1. **Сборка по скелету.** Три независимых эшелона: (а) агент —
   `manifest_build_ready` в `validate_command` (fail-closed: готовность выражена
   и флагом фазы, И структурно — непустые главы с длительностями; «забыть флаг»
   недостаточно, чтобы пробить структурную проверку; скелет без фазы невозможен —
   её ставит единственный скелетный писатель безусловно); (б) приложение —
   кнопка disabled до ready (то же определение, зеркалом); (в) движок —
   существующий `no_usable_chapters` как последний рубеж. Проверки I-E1.
2. **Гонка «ещё копируется».** Дебаунс остаётся ДО скелета (E10 не переезжает и
   не худеет — эти 0.5 c и есть пол). Два дешёвых ужесточения: после ожидания
   список mp3 перечитывается (файл, появившийся ВО ВРЕМЯ дебаунса, сегодня
   невидим для сравнения снапшотов); при N новых книгах — одно общее окно
   ожидания вместо N последовательных. Проверка I-E3. Случай «дроп продолжается
   после стабильного префикса» ловится, как и сегодня, сменой rev → re-arm; это
   не регрессия раннего нуджа (окно честно показывает «N файлов · X ГБ», и
   ре-арм обновит его).
3. **Леджер «одна публикация — один нудж».** Token чеканится ровно один раз — в
   скелете; все фазы переписывают манифест с его сохранением ⇒ ключ
   `book:<id>:<rev16>:<token16>` неизменен на публикациях #2–#4 ⇒
   `_publish_showcase_and_maybe_open` не находит новых рёбер. Второго нуджа нет
   **по построению**, а не по «не забудьте». Проверки I-E2/E5/E9.
4. **skip.** Порядок в проходе 1 не меняется: rev-проверка (stat-only, даром) —
   первой; совпавший rev при терминальной фазе возвращает манифест нетронутым —
   скелет не пишется, нуджа нет, воскрешения нет. Проверка I-E4 (плюс вся §skip).
5. **reconvert.** Force-путь (`rescan_book_manifest(force=True)`) сознательно НЕ
   фазируется: окно уже открыто, человек уже в приложении — пишем один полный
   манифест `phase=done` с новым token (легитимное новое ребро → ровно один
   re-нудж, как сегодня). Веб внутри reconvert остаётся синхронным — вне скоупа
   (см. §6). Проверка I-E11.
6. **refresh_showcase со скелетом на диске.** Скелет самодостаточен для
   проекции: главы (по именам файлов) дают честный счётчик, отсутствующая
   длительность уже сегодня скрывается очередью (`QueueView` рисует условно),
   строка несёт `phase` для подписи «читаю…». Окно подтверждения по скелету —
   штатный рендер фазы skeleton (§2.6), а не вырожденный кейс. Проверка I-E8 +
   Swift-юниты.

## 6. Что осознанно НЕ делаем

- **Не стримим главы по одной.** Проба всей книги — 0.25 c; десятки публикаций
  не дали бы ничего, кроме дёргающегося окна. Трёх-четырёх публикаций достаточно.
- **Не выносим веб в отдельный процесс/демон.** Модель «один запуск — один
  выход» сохраняется; веб просто переезжает в хвост того же процесса.
- **Не трогаем WEB_TIMEOUT_S / последовательность DDG→Яндекс.** После M-B сеть
  вне критического пути; её оптимизация — отдельная задача, если вообще нужна.
- **Не фазируем группы loose-mp3.** В их пути нет сети — нет и дисперсии; их
  пол уже ~0.8 c. Группа проецируется в проходе 1 как сегодня.
- **Не фазируем reconvert** (см. риск 5) и не трогаем его синхронный веб.
- **Не трогаем лестницу показа окна (D16)** и свежий фикс в
  `WindowPresentation`/`selfcheck_routing`: нудж остаётся `open -b`, видимостью
  владеет приложение.
- **Не добавляем новых команд протокола** и обратного канала «дай ещё» —
  дозаполнение идёт по существующему file-watch state/.
- **Не сокращаем и не переносим дебаунс E10** ради пола 0.3 c — риск №2 дороже.
- **Не «паркуем» confirm-команду против скелета до готовности** (defer в
  очереди): в честном клиенте кейс недостижим, а reject проще и наблюдаемее.

## 7. Открытые вопросы человеку

1. **Порядок ленты обложек.** Чтобы поздние веб-находки не сдвигали плитки под
   курсором, лента становится append-only: «Из файла» → «Вариант 1..N» →
   «Из сети 1..N» (веб — в конец). Раньше канонический порядок был
   embedded → web → generated. Принимаем новый порядок ради стабильности
   вёрстки? (Дефолтный выбор не меняется — веб и раньше никогда не был дефолтом.)
2. **Список глав на скелете.** Показываем сразу имена файлов (мгновенно полное
   окно; редкий одноразовый пересорт, если ID3-треки зададут иной порядок) — или
   шиммер-строки до пробы (+~0.3–0.5 c, зато ноль пересортов)? План рекомендует
   имена файлов: строки некликабельны, а одна атомарная коррекция — честная цена.
