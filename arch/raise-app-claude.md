## 1. Выбор пути: (А) агент будит приложение (`open` на rising edge)

**Рекомендация: путь А.** Обоснование:

1. **Агент — единственный, кто ЗНАЕТ момент rising edge.** Именно он создаёт
   `pending-confirm` и именно он в `run_scan` уже читает СТАРЫЙ `state.json` с диска
   ДО перезаписи (`prev = state.read_state(...)`, scan.py:1073). Сравнение «старый
   набор pending vs новый» — ноль дополнительного I/O, детектор уже наполовину написан.
2. **Путь Б ломает существующий дизайн приложения.** Приложение — обычное оконное
   (`setActivationPolicy(.regular)`, main.swift:4308) и НАМЕРЕННО завершается при
   закрытии окна (`applicationShouldTerminateAfterLastWindowClosed → true`,
   main.swift:4293). Login-item/LSUIElement требует: снять terminate-on-close,
   SMAppService-регистрацию, обработку «пользователь всё равно Cmd+Q» (гарантия
   умирает вместе с процессом, а «самовоскрешение» — враждебный UX). Это большая
   инвазивная переделка ради события, случающегося раз в день.
3. **Б ничего не выигрывает по надёжности.** Watcher приложения смотрит на
   `state/` в App Support (локальный диск, надёжно), но `state.json` меняется
   ТОЛЬКО когда отработал агент. Оба пути одинаково downstream от launchd-wake-up.
4. **А переиспользует уже написанную половину.** У работающего приложения rising
   edge уже реализован (`lastPendingIDs`/`lastGroupIDs` + `bringWindowForward`,
   main.swift:3728–3741, 4037–4054). `open -b` на уже запущенное приложение просто
   активирует его → `didBecomeActiveNotification` → `refreshNow()` (focus observer,
   main.swift:4010) → app-side edge сам покажет confirm. На НЕзапущенное — холодный
   старт, а landing-логика (`model.manifest != nil ? .confirm : .status`,
   main.swift:3759) уже открывает окно подтверждения. **В приложении менять нечего.**

**Про iCloud-Desktop:** ненадёжность `WatchPaths` на iCloud-папке влияет на то,
КОГДА проснётся агент, одинаково для обоих путей — она ортогональна этой правке.
Наш edge-детектор diff-based (сравнение состояний), а не event-based, поэтому он
совместим с любым будущим фиксом доставки событий (например, `StartInterval 60` в
plist как страховочный тик): пропущенное событие догоняется следующим запуском без
повторных всплытий. Добавлять `StartInterval` в ЭТОЙ правке не предлагаю (отдельное
решение, меняет энергопрофиль/plist) — но фиксирую совместимость.

## 3. Как снят каждый edge

### 3.1 Петля «агент открыл приложение → команда → WatchPaths → агент снова»

Разорвана конструктивно, тремя фактами:
1. Baseline — это `prev` state.json НА ДИСКЕ, и каждый `run_scan`/дрейн сам его
   обновляет. Confirm-цикл: команда → wake → scan-проход (книга была pending и
   осталась pending → diff пуст → нет nudge) → drain строит → закрывающий
   `run_scan()` (notify=False) записывает done → удаление файла команды → ещё один
   WatchPaths-wake → scan: prev=done, now=done → diff пуст. **Ноль всплытий.**
2. Reconvert/cancel/grouping-choice ре-армят pending ВНУТРИ дрейна, и закрывающий
   `run_scan(notify=False)` (или `refresh_showcase`) СНАЧАЛА записывает это в
   state.json; следующий notify-проход видит книгу pending уже в prev → diff пуст.
   Edge «потребляется» самой записью состояния, атомарно с ней.
3. Соседний работающий сценарий (пользователь в приложении) обслуживает app-side
   edge приложения (он уже есть) — агентский nudge для него не нужен и не случится.

### 3.2 Гонки

- **Приложение стартует в `.updating` (bundled≠staged):** ничего не ломается.
  `refreshNow` во время `.setup`/`.updating` не навигирует (main.swift:4023), а по
  успеху автообновления `handleInstalled()` пересчитывает landing: `manifest != nil
  → .confirm` + `bringWindowForward` (main.swift:3956–3964). Pending-книга всплывёт
  сразу после апдейта. При failed — окно приложения на переднем плане с честной
  ошибкой и «Повторить»; книга всплывёт после ретрая. Кода не менять, покрыть тестом.
- **Чтение state, пока агент пишет:** исключено атомарностью tmp→`os.replace`
  (state.py:26–52) — читатель видит старый ИЛИ новый файл, никогда рваный. Порядок
  в правке: `write_state()` ЗАВЕРШЁН → потом `open`. Холодный старт читает уже
  новое состояние; если вдруг старое (вторая книга прилетела в момент старта) —
  DispatchSource-watcher на `state/` догонит через ~150 мс (main.swift:3986–3993).
- **Два агента одновременно:** launchd не запускает вторую копию label, пока жива
  первая (события коалесцируются) → все `run_scan` сериализованы, single-writer цел.
- **`open` в момент Cmd+Q:** LaunchServices просто перезапустит приложение → landing
  `.confirm`. Безвредно.

### 3.3 Не красть фокус на уже виденное

- Уже-pending книги/группы есть в prev → diff пуст → nudge не срабатывает.
- `RunAtLoad` при логине: prev на диске тот же → нет всплытия при каждом входе в
  систему, даже если книга неделями висит pending.
- Self-wake от собственных записей агента (удаление файлов команд в
  `queue/commands/` — WatchPaths-путь): pending-набор не изменился → нет nudge.
- Изменение файлов УЖЕ pending-книги (source_rev flip, статус pending→pending):
  diff по book_id пуст → без всплытия (окно уже всплывало на первое появление) —
  осознанное решение против дёргания.
- Книга done → пользователь докинул файлы в её папку → scan ре-армит pending:
  book_id есть в prev, но статус был done → попадает в diff → всплытие. Корректно:
  это новое подтверждение, вызванное действием пользователя в файловой системе.
- E10 (полукопия): книга не армится, пока файлы нестабильны → nudge придёт со
  следующим wake-up'ом после стабилизации, один раз.

## 4. Риски и митигация

| Риск | Митигация |
|---|---|
| Crash агента в окне «write_state выполнен, open ещё нет» → edge потреблён, всплытия нет | Окно — миллисекунды; самолечится на следующей новой книге. Отдельный «notified-ledger» = второй регистр состояния — осознанно НЕ делаем (оверинжиниринг) |
| macOS 14+ ужесточил кражу фокуса: активация может не отдать key-фокус | `open` идёт через LaunchServices (самый «легитимный» канал активации) + приложение само зовёт `NSApp.activate(ignoringOtherApps:)`. Худший случай — окно поверх, Dock-иконка прыгает: всё равно на порядок лучше текущего |
| Self-check, гоняющий `python3 -m agent` end-to-end, всплывёт реальное приложение | Правило подавления: `MP3TOM4B_SUPPORT_DIR` задан (все тесты — scratch) и `MP3TOM4B_NUDGE_CMD` не задан → nudge молчит. Существующие self-check'и не трогаем; позитивный тест задаёт `MP3TOM4B_NUDGE_CMD` на рекордер |
| `open` подвис (LaunchServices деградировал) | `timeout=15`, `check=False`, DEVNULL; сборка в том же запуске не блокируется, событие в журнале |
| WatchPaths на iCloud-Desktop теряет события → агент вообще не просыпается | Вне скоупа этой правки; дизайн diff-based → безопасно совместим с будущим `StartInterval` страховочным тиком (вопрос человеку ниже) |

# ЧАСТЬ 2 — Корректировка: повторный дроп уже-собранной книги (2026-07-07)

> Механизм побудки (Часть 1) реализован и НЕ пересматривается. Пересмотрена ТОЛЬКО
> привязка «когда книга становится pending». Модель человека: любое сознательное
> помещение папки в отслеживаемую = намерение (пере)конвертировать, даже при
> идентичном контенте. Сейчас повторный дроп done-книги дедупается молча —
> `_write_manifest` short-circuit по `source_rev` (scan.py:585–594): Finder при
> копировании СОХРАНЯЕТ mtime файлов, поэтому relpath+size+mtime_ns совпадают,
> манифест возвращается как есть со статусом `done`. Это и есть баг.

## 1. Рекомендованный сигнал дропа: st_ino каждого файла ВНУТРИ source_rev (rev v2)

**Сигнал: включить `st_ino` каждого mp3 в фингерпринт `source_rev_for`**
(scan.py:299–319): `relpath\0size\0mtime_ns\0st_ino`. Копирование папки — это
ВСЕГДА создание новых файлов → новые inode, независимо от того, что Finder
восстанавливает timestamps. Повторный дроп идентичного контента ⇒ rev меняется ⇒
срабатывает **уже существующий** путь ре-арма «changed source_rev rewrites the
manifest and re-arms pending-confirm» (scan.py:24–26, 583–599). Ноль новых
механизмов ре-арма.

**Почему НЕ кандидаты из брифа:**
- *mtime папки > built_at* — ненадёжен в главном жесте: Finder после копирования
  ВОССТАНАВЛИВАЕТ mtime самой скопированной папки (атрибуты источника), т.е. у
  свежеположенной папки mtime часто СТАРШЕ `built_at` → пропуск. Плюс у
  combined-книг `src_dir` = корень отслеживаемой папки (scan.py:707), чей mtime
  шумит на каждом событии (включая запись нашего же .m4b в корень) → ложные
  всплытия.
- *«исчезла-и-появилась» (трек присутствия)* — требует, чтобы агент ЗАСТАЛ
  промежуточное отсутствие между wake-up'ами; delete+recopy между двумя запусками
  (или потерянное iCloud-событие) делает наблюдение недостоверным. Inode кодирует
  «это физически другой файл» БЕЗ необходимости видеть переход.

**Надёжность на iCloud-Desktop:** ~/Desktop — локальная APFS-директория (bird
синхронизирует поверх). `st_ino` реальный и стабильный. Eviction («Убрать
загрузку») делает файл dataless — это флаг на ТОМ ЖЕ inode, unlink нет →
rematerialization не меняет ino → лежащие книги молчат. Частичная синхронизация:
недокачанный файл ловится существующим E10-дебаунсом (size/mtime нестабильны →
книга не армится этот проход, scan.py:355–372). Дроп с другого Mac через iCloud:
bird создаёт файлы локально → новые ino → корректное всплытие (это и есть
сознательный дроп пользователя). Timestamps тут вообще не участвуют — главная
причина выбора ino, а не времени.

**Бонус:** `group_rev_for` делегирует в `source_rev_for` (scan.py:296) →
повторный дроп loose-mp3 автоматически даёт новый group rev → новый
`grouping_idempotency_key` → ledger `grouping_processed` больше не глушит
повторный промпт. Параллельный такой же баг закрывается бесплатно.

**Известный пропуск (осознанный):** перемещение папки в пределах одного тома
(move out → move back) сохраняет inode → rev тот же → молчание. Опциональное
расширение P2 (не в этой правке): «reappeared»-сигнал по prev state.json (book_id
отсутствовал в прошлой витрине, манифест done, папка снова жива → ре-арм) —
best-effort, работает только если промежуточный скан застал отсутствие.

## 2. Место/механизм пере-вооружения

**Файл: `agent/scan.py`, функция `source_rev_for` + миграционная ветка в
`_write_manifest`.** Новый путь ре-арма НЕ создаётся — работает существующий:

1. `source_rev_for` (scan.py:299): добавить `st.st_ino` в строку хэша (v2).
   Vanished-файл — маркер `-1`, как сейчас.
2. `_write_manifest` (scan.py:583–599) — rev у done-книги при повторном дропе не
   совпадает → short-circuit не срабатывает → падаем в существующую ветку записи:
   свежий манифест со `status=pending-confirm`, НОВЫЙ `confirm_token`
   (scan.py:610), НОВЫЙ `source_rev`, `processed_keys: []` (scan.py:622–627).
   Идемпотентность чинится дважды: (а) ledger пуст; (б) приложение выводит
   idempotency_key из book_id + НОВОГО rev[:16] — такого ключа ни в одном старом
   ledger нет физически. `idempotent_skip` (dispatcher.py:187–188) невозможен →
   реальная пересборка. E10-дебаунс сохраняется (`debounce=True` на пути
   `write_manifest_for_book`, scan.py:670) — полукопия не армится.
3. **Миграция (обязательна, иначе шторм всплытий после обновления агента):** у
   всех существующих манифестов rev в формате v1 → при первом скане v2-rev не
   совпадёт у ВСЕХ книг → N ложных ре-армов. Гард в `_write_manifest` перед
   основной веткой: если `existing.source_rev == source_rev_legacy_for(mp3s,
   base_dir)` (v1-хэш без ino, сохранить как отдельную функцию) → это смена
   ФОРМАТА, не дроп: молча проставить v2-rev in place (атомарная перезапись с
   сохранением status/confirm_token/processed_keys) и вернуть манифест БЕЗ
   ре-арма. Аналогично в `_build_pending_group` (scan.py:466): проверять resolved
   ledger по ОБОИМ ключам (v2 и legacy); если совпал legacy — дозаписать v2-ключ
   через `record_grouping_resolved` и не промптить.
4. Побудка (Часть 1) подхватывает автоматически: ре-арм происходит в scan-проходе
   `run_scan(notify_app=True)` → done→pending попадает в diff pending-набора →
   существующий `open -b`. Ни одной строчки в механизме побудки не меняется.

## 3. Доказательство «0 всплытий на логине» (RunAtLoad, N лежащих done-книг)

- **Steady state:** файлы не тронуты → у каждого mp3 (relpath, size, mtime_ns,
  ino) идентичны → v2-rev == сохранённого → short-circuit (scan.py:588–594)
  возвращает манифест как есть, `done` → pending-набор витрины == prev state.json
  → diff побудки пуст → 0 `open`. Сигнал по построению молчит без физической
  замены файлов: логин не меняет ни ino, ни mtime.
- **Первый логин после обновления агента (legacy-манифесты):** v2-rev ≠
  сохранённого, но legacy-rev == сохранённого → ветка молчаливого апгрейда (п.2.3):
  статус сохранён (done остаётся done), pending-набор не меняется → 0 всплытий.
- Уже-pending книги на логине: их id уже в prev → diff пуст (доказано в Части 1,
  §3.3).

## 4. Анти-петля и совместимость с реализованной побудкой

- **После «Собрать»:** confirm → converting → done. Сборка только ЧИТАЕТ исходники
  (I1) → ino/mtime/size нетронуты → rev стабилен → последующие сканы
  short-circuit'ятся, ре-арма нет. Готовый .m4b пишется РЯДОМ с папкой книги, в
  корень отслеживаемой (`build_m4b.default_output_path`, build_m4b.py:335–351 —
  «next to the source folder, same parent»), НЕ в `src_dir` → папку книги не
  мутирует. Запись .m4b будит агента (корень в WatchPaths), но diff пуст → тишина.
- Ре-армы внутри дрейна (reconvert/cancel/grouping) по-прежнему идут через
  `notify=False`-запись baseline (Часть 1, §3.1) — не всплывают.
- Побудка не меняется: тот же diff prev↔new pending-набора; новая правка лишь
  делает так, что сознательный ре-дроп ЛЕГИТИМНО попадает в этот diff.

## 5. Риски и митигация (Часть 2)

| Риск | Митигация |
|---|---|
| Шторм ре-армов после обновления агента (смена формата rev) | Обязательная legacy-ветка миграции (п.2.3): v1-совпадение = молчаливый апгрейд rev in place, 0 всплытий. Аналогично для grouping-ledger (оба ключа) |
| Гипотетическая смена ino при iCloud-rematerialization на какой-то версии macOS | Худший случай — ОДИН лишний вопрос-подтверждение (окно), никогда не молчаливая сборка и не потеря данных. Fail-safe по построению |
| Watch-папка на FAT/exFAT томе (Settings позволяет): синтетические ino нестабильны между монтированиями → ложные ре-армы после ремонта | Принятый риск (дефолт — APFS Desktop); последствия — лишние подтверждения, не порча. Проставить в манифест поле `source_rev_v: 2` на будущее, если понадобится per-volume логика |
| Self-check'и, пересоздающие идентичные файлы в расчёте на стабильный rev | Прогнать `selfcheck_all`; такие ожидания теперь НЕВЕРНЫ по новой спецификации (пересоздание = новый rev) — обновить ассерты, это не регрессия |
| Пользователь держит окно подтверждения открытым в момент апгрейда rev (миграция) | Команда со старым rev → существующий REJECT_STALE (dispatcher.py:190–194), книга остаётся pending, окно перечитает свежий манифест через file-watch. Самолечится |
| Move-back в пределах тома не ловится (ino сохранён) | Осознанный пропуск; P2-расширение «reappeared»-сигналом (п.1), отдельным решением |

**Чего НЕ делать (Часть 2):** не добавлять отдельный «redrop-детектор» по mtime
папки / presence-треку (отвергнуты в п.1); не трогать механизм побудки,
dispatcher, приложение, installer/plist; не менять протокол команд — приложение
эхоит rev/token, которые читает из манифеста, ему всё равно, v1 это или v2.
