# Ускорение движка mp3→.m4b — план Архитектора #1 (Claude)

> READ-ONLY анализ + план. Код не менялся. Все числа ниже — реально прогнаны на этой машине
> (macOS arm64, ffmpeg 8.1.2 Homebrew с `--enable-audiotoolbox`, 16 ядер = 12P+4E,
> Python 3.14). Синтетика: 8 глав × 180 с = 24 мин аудио, 192 kbps стерео 44100.

---

## Итог (3–5 строк)

Узкое место — **один серийный AAC-энкод одним процессом**: `-threads` на аудио НЕ влияет
(проверено: 12.77 с vs 12.83 с). Есть две независимые оси ускорения: **(A) сменить энкодер
на Apple `aac_at`** (×1.24 даром, gapless цел) и **(B) кодировать главы ПАРАЛЛЕЛЬНО по ядрам**
+ stream-copy склейка (×6–8, near-linear). Параллель даёт огромный выигрыш, но «в лоб» **ломает
бесшовность**: каждая глава кодируется как самостоятельный поток → AAC добавляет на стыке
~23 мс тишины (priming+хвостовой паддинг до целого фрейма) — проверено `silencedetect` ровно на
180/360/540/720 с. Для **речи** 23 мс попадают в естественную паузу между главами и не слышны;
драма только для непрерывной музыки. Моя рекомендация — **двухступенчато**: сначала бесплатный
безрисковый `aac_at` (1 строка), затем параллель-по-главам с метками глав из **измеренных**
длительностей частей (а не исходных mp3 — иначе дрейф меток).

## Бенчмарк (24 мин аудио, 12P+4E, 192k) — фактические числа

| подход | время | ускор. ×тек. | gapless | дрейф меток |
|---|---:|---:|---|---|
| **single-pass native `aac`** (текущий движок) | 12.86 с | 1.0 | ✅ да | нет |
| single-pass `aac_at` (CBR) | 10.36 с | 1.24 | ✅ да | нет |
| single-pass `aac_at` (VBR `-q:a 9`) | 5.48 с | 2.35 | ✅ да | нет (но размер VBR-зависим) |
| **параллель per-chapter `aac` + copy** (8 worker) | 2.01 с | **6.4** | ❌ +23 мс/стык | да, если марки из mp3 |
| **параллель per-chapter `aac_at` + copy** (8 worker) | 1.62 с | **7.9** | ❌ +23 мс/стык | да, если марки из mp3 |
| параллель `aac_at`, 4 worker | 1.63 с | 7.9 | ❌ | — |

Замечания по числам:
- `-threads 1` vs `-threads 8` на single-pass: **12.77 / 12.83 с** → аудио-энкод одного потока
  НЕ параллелится; единственный путь к многоядерности — резать поток на куски.
- copy-склейка частей (concat-demuxer `-c copy`) — **0.15 с** на 24 мин (мукс почти бесплатный).
- worker 4 vs 12 на 8 главах: 2.82 / 1.48 с — параллелизм реален (Apple AudioToolbox не
  сериализуется), упирается в число активных глав и ядра. Оптимум ≈ `min(N_глав, N_ядер)`.
- `aac_at` имеет режимы `-aac_coder`/VBR: `cbr/abr/cvbr/vbr`; VBR (`-q:a`) заметно быстрее и
  для голоса часто чище на бит, но размер плавает — для «оценки размера в окне подтверждения»
  это означает, что при VBR оценку надо помечать как приблизительную.

## Корень проблемы бесшовности (доказано)

AAC кодирует фреймами по 1024 сэмпла. Любой **конечный** поток энкодер:
1. предваряет **priming** (~1 фрейм энкодер-делея);
2. добивает хвост **паддингом** до целого фрейма.

В **одном** m4b это лечится единым **edit list (elst)** в moov: контейнер обрезает priming/паддинг,
плеер играет ровно. Проверено: single-pass = 518 фреймов, но decoded = 1440.009 с, внутренних
тишин 0.

При **независимом** кодировании каждой главы у КАЖДОЙ части свои priming+паддинг, «зашитые в
сэмплы». stream-copy склейка их НЕ убирает (единого elst через стык нет). Проверено:
- decoded параллель = 1440.19 с (native) / 1440.57 с (aac_at) против 1440.00 истинных;
- `silencedetect` срабатывает на КАЖДОЙ границе главы (180/360/540/720 с), ~23 мс тишины.
- ADTS (raw `.aac`) концат — то же самое (8 событий тишины): паддинг инт­ринсик к кодированию
  куска, контейнерным трюком не снимается.

**Два следствия:**
- **Слышимость:** +23 мс на стыке для речи = безобидное удлинение и без того существующей паузы
  между главами; для аудиокниги практически неразличимо. (Gapless критичен для музыки/кроссфейдов.)
- **Дрейф меток:** если START/END глав считать из ИСХОДНЫХ длительностей mp3, они «уползут» от
  реального (паддингованного) потока — к концу 56-главой книги до ~1.3 с. **Фикс:** считать метки
  из **измеренных ffprobe длительностей готовых частей**. Проверено: при марках из probed-частей
  главы выходят строго стыкованными (0/180/360/…/1440 с), потому что контейнер каждой части
  рапортует ровно 180.000 с (его elst срезает priming на уровне части), и накопленная сумма
  совпадает с потоком. Метки остаются «на аудио».

## Ранжированные опции (быстрая победа → максимум)

### Опция 0 — `aac_at` вместо `aac` (БЫСТРАЯ ПОБЕДА, near-zero риск)
- **Что:** заменить `-c:a aac` → `-c:a aac_at` в обоих путях (filter и demuxer).
- **Выигрыш:** ×1.24 (CBR) сразу; gapless ЦЕЛ, архитектура не меняется, отмена/прогресс работают
  как есть (это всё ещё ОДИН ffmpeg).
- **Риск:** минимальный. `aac_at` — системный энкодер Apple, приложение macOS-only. Нюанс:
  `aac_at` поддерживает входные форматы `s16/u8` (фильтр `aformat` уже нормализует — добавить
  `sample_fmts=s16` в граф для надёжности). На QA сверить качество голоса на 96–192k.
- **ffmpeg-вызов (изменение точечное):**
  ```
  -c:a aac_at -b:a {bitrate}k -ar {sr} -ac {ch}
  ```
- **Где в коде:** `_build_with_filter` и `_build_with_demuxer` — строка `"-c:a", "aac"`.
  Плюс константа выбора энкодера + детект доступности `aac_at` (см. ниже «дешёвые победы»).

### Опция A — ПАРАЛЛЕЛЬ per-chapter + stream-copy склейка (МАКСИМУМ ×6–8)
Это главный приз. Архитектурно — самый большой шаг, но контракты сохраняемы.

**Конвейер (новая функция `_build_parallel`, выбирается при `len(chapters) >= 2`):**
1. **Пул процессов** (`concurrent.futures.ThreadPoolExecutor`, т.к. ffmpeg — внешний процесс,
   GIL не мешает; max_workers = `min(N_глав, os.cpu_count())`). Каждая глава →
   промежуточный `.m4a` в temp-папке внутри out_dir:
   ```
   ffmpeg -hide_banner -loglevel error -y -i <ch_i.mp3> \
     -c:a aac_at -b:a {bitrate}k -ar {sr} -ac {ch} \
     -f mp4 <tmpdir>/part_<NNN>.m4a
   ```
   (единые SR/каналы/битрейт на ВСЕ части — это и есть условие корректной copy-склейки.)
2. **Измерить** ffprobe каждую готовую часть (`format=duration`) → накопить START/END глав в мс
   из ЭТИХ длительностей (НЕ из manifest `duration_ms`) → FFMETADATA.
3. **Склейка stream-copy** одним ffmpeg (concat-demuxer, без ре-энкода) + метаданные/обложка/
   faststart:
   ```
   ffmpeg -hide_banner -loglevel error -y \
     -f concat -safe 0 -i <list.txt> \
     -i <ffmeta_probed.txt> -i <cover.jpg> \
     -map 0:a -map 2:v -map_metadata 1 -map_chapters 1 \
     -c copy -c:v mjpeg -disposition:v attached_pic \
     -f ipod -movflags +faststart <tmp_out>
   ```
   `-map_chapters 1` критичен (research §3-грабли: иначе ffmpeg тащит главы и из частей, и из
   файла → дубли). Обложка — `mjpeg` (как сейчас), `-c copy` относится к аудио.
4. `os.replace` temp→final (как сейчас), затем смести `tmpdir` с частями.

**Выигрыш:** near-linear по `min(N_глав, ядра)` — ×6.4 (native) / ×7.9 (aac_at) на 8 главах/12 ядрах.
На 56-главой книге выигрыш ещё выше (больше параллелизма).

**Цена корректности:** +~23 мс тишины на стык (для речи неслышно). Если когда-нибудь понадобится
БИТ-в-бит бесшовность — её даёт только single-pass; параллель и бесшовность взаимоисключающи
(доказано: `-threads` аудио не параллелит). Это явный trade-off для человека на СТОП-точке.

### Опция B — параллель native `aac` + copy (если `aac_at` почему-то недоступен)
Идентична A, но `-c:a aac`. ×6.4. Фолбэк, когда `aac_at` не детектится (нестандартная сборка
ffmpeg) — хотя на целевой macOS он есть всегда (`--enable-audiotoolbox` в Homebrew-бутылке).

### Опция C — single-pass `aac_at` VBR (×2.35, бесшовно, но размер плавает)
Если параллель решат НЕ внедрять (например, бескомпромиссная бесшовность важнее), VBR-режим
`aac_at` даёт ×2.35 даром и для голоса часто чище. Минус: размер непредсказуем → оценка в окне
подтверждения становится грубее. Держать как опцию, не как дефолт.

## Дешёвые победы и тюнинг (п.4 брифа)

- **Пропуск `aformat`, если источник уже = целевым SR/каналам?** Даёт копейки: `aformat` — это
  ресэмпл/ремикс в фильтре, его стоимость ничтожна на фоне самого AAC-энкода (узкое место —
  энкодер, не фильтр). Микрооптимизация, НЕ внедрять как отдельную фичу (усложняет граф ради
  ~0). Параллель убирает её значимость полностью.
- **stream-copy без энкода вообще?** Невозможно для mp3 (research §1a: `[ipod] Could not find
  tag for codec mp3 … not supported in container` — проверено). Если источник УЖЕ AAC/m4a/m4b —
  теоретически `-c copy`, но для **mp3-книг** это вне сценария (вход всегда mp3). Не закладывать.
- **`-threads`:** на аудио-энкод не влияет (12.77/12.83 с) — НЕ трогать, это не рычаг.
- **filter threads (`filter_complex_threads`):** граф тривиальный (aformat+concat), не bottleneck —
  не рычаг.
- **Детект `aac_at`:** один раз за процесс — `ffmpeg -hide_banner -encoders | grep -q aac_at`
  (по образцу `scan.engine_version()` с кэшем). Выбор энкодера: `aac_at` если есть, иначе `aac`.

Прогресс/отмена контракт сохраняется. |

**Инварианты, которые НЕ меняются:** только ffmpeg/ffprobe; выход — валидный `.m4b` (`-f ipod`,
главы 1/1000, обложка attached_pic, faststart); атомарный temp→rename; I1 (mp3 только читаются);
кооперативная отмена SIGTERM→SIGKILL без осиротышей.

## Стыковка с ПРОГРЕССОМ (тот же контракт, UI не меняется)

Контракт state.json: `percent / current_chapter_index / current_chapter_name / eta_s /
elapsed_s / total_chapters`. Сейчас питается из `out_time` одного ffmpeg.

**Single-pass (Опция 0):** без изменений — парсинг `-progress`/`out_time` одного процесса.

**Параллель (Опция A) — как считать:**
- `total_chapters = N`. **Гранулярность = глава** (а не «текущее время одного ffmpeg»).
- `chapters_done` = число завершившихся воркеров (атомарный счётчик из callback пула).
- `current_chapter_index` = наименьший ещё-не-готовый индекс (или последний завершённый — на
  выбор UX; «N из M» читается естественно как `chapters_done`).
- `current_chapter_name` = имя этой главы из manifest.
- **`percent`** = взвешенно по ДЛИТЕЛЬНОСТИ: главы разной длины. Базовый «дробь»:
  `percent = sum(duration_ms готовых глав) / total_duration_ms × 0.95`. Оставить 0.95 как
  «энкод», финальные 5% — на этап concat-copy+faststart (он короткий, но даёт «движение» в конце).
  Точнее «дроби текущих»: можно парсить `-progress` каждого активного воркера и добавлять частичный
  вклад (`out_time_i/dur_i × вес_i`), но это усложняет; для V1 достаточно поглавной гранулярности
  (на 56 главах шаги мелкие и UI выглядит плавно).
- **`eta_s`** = по фактической скорости: `elapsed/percent − elapsed`. Стабильнее одиночного ffmpeg,
  т.к. усредняется по многим главам.
- **`elapsed_s`** = `now − started_at` (уже есть в `manifest["build"]["started_at"]`).
- Запись прогресса: воркер-callback обновляет `manifest["progress"]`/прогресс-поля атомарно и
  зовёт `scan.refresh_showcase()` (как сейчас делает `_real_build` на переходах) — но НЕ чаще
  ~раз в 0.3–0.5 с (троттлинг, чтобы не молотить диск). Это ложится на существующий poll-цикл.

**Вывод:** UI получает ТОТ ЖЕ контракт; меняется только источник чисел (поглавный счётчик вместо
`out_time`). Поля заполняются все.

## Стыковка с ОТМЕНОЙ (D13) и SR-из-источника

- **Отмена:** существующая модель «агент гасит СВОИ ffmpeg-дети» масштабируется на N процессов.
  Ключ: держать список живых `Popen` частей; poll `_cancel_requested(book_id)` в общем цикле →
  `_terminate_ffmpeg` по каждому → отменить незапущенные таски пула → sweep temp-папки → поднять
  `BuildCancelled`. Никаких kill по pid извне; никаких осиротышей. `converting→pending-confirm`
  как сейчас (обработчик `BuildCancelled` в `_real_build` не меняется).
- **SR-из-источника:** дефолт SR книги (`params.samplerate==None` → `source_samplerate`, max по
  главам) полностью уважается — он просто пробрасывается в `-ar {sr}` КАЖДОЙ части и в финальный
  мукс. Важно: ВСЕ части кодируются в ОДИН и тот же SR/каналы/битрейт — это и есть предусловие
  корректной `-c copy` склейки (разные параметры частей → copy-склейка невалидна). `aformat`/`-ar`
  в каждом воркере это гарантирует даже при разнородных входах (mixed SR).

## Риски и краевые (п.6)

- **Бесшовность (главный):** +~23 мс/стык в параллели. Для речи неслышно; для музыки — слышно.
  Доказано `silencedetect`. **СТОП-точка человеку:** ок ли это для аудиокниг (моё мнение — да),
  или нужен бескомпромиссный single-pass (тогда Опция 0/C).
- **Дрейф меток:** лечится метками из **probed** длительностей частей (доказано — стыкуются ровно).
  Если забыть и взять `duration_ms` — уползёт до ~1.3 с/56 глав. Это явная ловушка реализации →
  в тест-план обязательный assert: `chapter.END[-1] == probed_total_duration ± 1 фрейм`.
- **Диск:** параллель пишет N промежуточных `.m4a` (суммарно ≈ размер финала, т.к. уже AAC) ДО
  склейки. Пик использования диска ≈ 2× финал (части + результат). E5 free-space pre-flight надо
  поднять с `required_free_space` до ~2× на параллель-пути (или сметать каждую часть сразу после
  включения в… — нет, demuxer-copy читает все части на этапе мукса, сметать можно только ПОСЛЕ
  склейки). → **изменить `_ensure_free_space`** на множитель для параллели.
- **Сложность:** параллель добавляет пул, temp-папку, агрегацию прогресса, групповую отмену — это
  заметный рост против «один ffmpeg». Опция 0 такого не несёт. Поэтому двухступенчатость.
- **1 глава (N==1):** параллелить нечего; идём single-pass (нет стыков → тривиально бесшовно).
  Явная ветка.
- **Очень много глав (N > 100, текущий `CONCAT_FILTER_MAX_CHAPTERS`):** параллель не держит сотни
  входов открытыми одновременно (в отличие от concat-FILTER) — пул ограничен `cpu_count`, склейка
  через concat-DEMUXER (последовательное открытие). Так что параллель СНИМАЕТ старое fd-ограничение.
  Но N temp-файлов на диске — следить за лимитом inode/места. На 56 главах проблем нет.
- **mixed SR:** каждая часть приводится к целевому SR (`-ar`), copy-склейка валидна. Без приведения
  copy сломается — поэтому `-ar/-ac` в каждом воркере обязательны (не полагаться на «и так совпало»).
- **Сбой одного чанка из N:** любой воркер с non-zero exit → отменить остальные, sweep temp-папку,
  поднять `BuildError` (как E3 — лучше упасть, чем отдать книгу без главы). `_run_ffmpeg` уже даёт
  reason+хвост stderr; пробросить какой именно чанк упал в `detail`.
- **`aac_at` качество:** на очень низких битрейтах (<96k) Apple-энкодер обычно лучше native, но
  это надо подтвердить на QA для голоса. Дефолт 192k — оба хороши. Без регресса.

## РЕКОМЕНДАЦИЯ — что внедрять первым

**Ступень 1 (сразу, минимум риска): Опция 0 — `aac_at`.** Одна правка литерала энкодера + детект
доступности. ×1.24 даром, gapless цел, отмена/прогресс/атомарность не трогаются. Это «дешёвая
победа» из брифа.

**Ступень 2 (главный приз, после согласования trade-off бесшовности): Опция A — параллель
per-chapter + stream-copy** на `aac_at`. ×6–8. Обязательные условия корректности (в тест-план):
(1) метки глав из **probed** длительностей частей; (2) единые SR/каналы/битрейт всех частей;
(3) групповая отмена всех ffmpeg; (4) поглавный прогресс в тот же контракт; (5) 2× free-space;
(6) sweep temp-частей на любом исходе.

**Почему так, а не сразу A:** Опция 0 окупается мгновенно и бесплатно страхует (если с параллелью
вылезут проблемы на реальных книгах — у нас уже есть ×1.24 без рисков). А ×6–8 требует СТОП-точки:
человек должен подтвердить, что +23 мс на стыке (неслышно для речи) приемлемо вместо
бит-в-бит бесшовного single-pass. Две головы на разных LLM именно для таких развилок.

**Вопрос к человеку (СТОП):** аудиокнига = речь, +~23 мс тишины на границе главы практически
неразличимы (это лишь чуть удлиняет естественную паузу). Подтверждаешь, что ради ×6–8 это
приемлемо? Если нужна бескомпромиссная бесшовность — берём `aac_at` VBR single-pass (×2.35,
бесшовно) и параллель не делаем.

## Приложение: точные команды (проверены)

**Опция 0 — single-pass aac_at (правка текущего):**
```
ffmpeg -hide_banner -loglevel error -y \
  -i ch1.mp3 ... -i chN.mp3 -i ffmeta.txt -i cover.jpg \
  -filter_complex_script fc.txt -map "[aout]" -map <cover>:v -map_metadata <meta> \
  -c:a aac_at -b:a 192k -ar 44100 -ac 2 \
  -c:v mjpeg -disposition:v attached_pic \
  -f ipod -movflags +faststart out.m4b
```

**Опция A — параллель (per worker):**
```
ffmpeg -hide_banner -loglevel error -y -i ch_i.mp3 \
  -c:a aac_at -b:a 192k -ar 44100 -ac 2 -f mp4 tmp/part_i.m4a
```
**Опция A — финальная склейка (stream-copy):**
```
ffmpeg -hide_banner -loglevel error -y \
  -f concat -safe 0 -i list.txt -i ffmeta_probed.txt -i cover.jpg \
  -map 0:a -map 2:v -map_metadata 1 -map_chapters 1 \
  -c copy -c:v mjpeg -disposition:v attached_pic \
  -f ipod -movflags +faststart out.m4b
```
где `ffmeta_probed.txt` использует НАКОПЛЕННЫЕ `ffprobe -show_entries format=duration` каждой
`part_i.m4a` (а не `manifest.duration_ms`).
