## 0. Суд: кто в чём прав

**Сошлись независимо (сильный сигнал — берём без обсуждения):**
- поле фазы в манифесте вместо булева «готово»;
- **скелет замёрзнет навсегда**, если не тронуть короткое замыкание по `source_rev`: у скелета rev
  уже финальный, замыкание вернёт его «как есть» и он никогда не дозаполнится. Оба нашли сами;
- один нудж держится тем, что `confirm_token` чеканится **один раз, на скелете**, а не дисциплиной;
- на стороне приложения главная опасность — **SwiftUI не пересеет поля сам**: `@State` для того же
  `book_id` переживёт обновление манифеста и съест новые данные.

**#1 сильнее — беру за основу:**
- **Веб-поиск обложек уходит с критического пути ЦЕЛИКОМ:** порядок процесса становится
  `scan(локальное) → drain → веб-обогащение`. Это решает исходную задачу, а не переносит её.
  План #2 держит `ready` за полной cover-chain, и он сам честно признаёт: при мёртвой сети те же
  ~12 с просто переезжают с «нет окна» на «окно есть, кнопка серая». Это не решение.
- **Скелет НЕ пустой:** имена глав из имён файлов, автор/название из имени папки, размер — всё
  достаётся даром из того же `stat`-прохода, что и `source_rev`. Окно сразу показывает книгу, а не
  спиннер.
- фазы `skeleton → chapters → ready → done`, **отсутствие поля = done** ⇒ старые манифесты
  совместимы автоматически, без миграции.

**#2 сильнее — прививаю к основе:**
- **Отдельный `build_token`, физически создаваемый только в финальной атомарной записи.**
  Это строго сильнее проверки фазы. Дыра, которую видит только #2: приложение пишет команду по
  скелету → команда лежит в очереди до drain → агент дописывает полный манифест с ТЕМ ЖЕ
  `source_rev` и `confirm_token` → валидатор смотрит на фазу «сейчас», видит `ready` и **принимает
  команду, рождённую по скелету**. У скелета `build_token` отсутствует физически, поэтому ранняя
  команда остаётся невалидной и после финализации. «Три эшелона» #1 этот TOCTOU не закрывают явно.
- **`_files_are_stable` сравнивает УЖЕ СОСТАВЛЕННЫЙ список** (`agent/scan.py:816`), каталог не
  перечитывает ⇒ файл, доехавший после составления списка, не замечается: можно получить
  «стабильные» 20 из копирующихся 56. **Это существующий баг, не привнесённый D17.**
- **Сетевой таймаут нельзя приводить к `folder_access=blocked`:** несколько офлайн-книг перебьют
  `PHASE_DEADLINE_S = 150` и покажут человеку ложную проблему с доступом к папке. После нашей
  основы (веб вне критического пути) риск падает, но страховка обязана быть явной — мы полгода
  воевали с настоящим TCC, ложная тревога тут особенно дорога.
- **Второй подъём окна мимо леджера:** rising-edge в `app/main.swift:5513` считает новизну по
  множеству `pendingConfirm`. Скелет в фазе «ещё читаем» туда не попадёт — значит окно поднимет
  агент ранним нуджем, а когда манифест перевернётся в `pending-confirm`, **приложение поднимет
  его второй раз своим каналом**, мимо агентского леджера. Найдено сверкой кода, не Sol'ом.
- generation-scoped имена файлов обложек (иначе воркер прошлой подготовки пишет в пути новой);
- жёсткий порядок публикации: **манифест → `state.json` → леджер → нудж** (состояние не имеет
  права объявить готовность раньше манифеста);
- `write_json_atomic` (`agent/state.py:26`) не делает fsync родительского каталога;
- атомарность одного JSON ≠ транзакция «манифест + состояние»;
- batch-публикация при пачке книг (публикация скелетов по одному ломает rapid-fire).

**Отвергнуто (обоснования принимаю):** булево `metadata_complete` — не отличает «ищем в сети» от
«ждать нечего» · нудж ДО дебаунса — риск «книга ещё копируется» дороже 0.5 с · отдельный файл
скелета — рвёт идентичность ключей леджера · отложенное исполнение команды по скелету — отказ
наблюдаемее.

**Осознанная цена (принимаю):** при падении между записью в леджер и нуджем уведомление теряется
навсегда. Это цена строгого «не более одного раза»; страховочный тик `StartInterval=300` книгу не
потеряет, но окно в этот раз не поднимет.

## 1. Целевая картина

```
дроп папки
  ├─ 0.00 с  launchd будит агента (WatchPaths, ThrottleInterval=5)
  ├─ 0.25 с  старт процесса + импорты
  ├─ 0.76 с  дебаунс _files_are_stable — ОСТАЁТСЯ ПЕРЕД НУДЖЕМ (риск «копируется»)
  ├─ 0.77 с  СКЕЛЕТ: имена глав из имён файлов, автор/название из папки, размер, confirm_token
  │          публикация #1 → леджер → НУДЖ  ─────────────►  ОКНО (~0.8 с)
  ├─ ~1.0 с  probe 56 файлов параллельно → настоящие главы, длительности, ID3
  ├─ ~1.3 с  embedded-обложка → фаза ready → build_token → «Собрать» АКТИВНА
  ├─         (без embedded: ~2.4 с — сгенерированные варианты)
  └─ после drain: веб-обогащение обложек — вне критического пути, лента дополняется
```

**Ключевое свойство:** ни окно, ни активность «Собрать», ни старт сборки больше не зависят от сети.

## 2. Milestone

| M | что | зависит от | параллельно с |
|---|---|---|---|
| **M-A** | протокол на агенте: фазы, скелет, `confirm_token` на скелете, **`build_token` в финальной записи**, resume, порядок публикации, гейт в `dispatcher` | — | — (строго первым: фиксирует спеку поля) |
| **M-B** | веб-обогащение обложек с критического пути (`scan → drain → enrich`), generation-scoped имена, таймаут ≠ `blocked` | M-A | M-C |
| **M-C** | приложение: рендер фаз без мигания, **чистая merge-функция** вместо присваиваний в `@State`, `isBuildReady` по `build_token`, **гашение второго подъёма окна** (rising-edge :5513) | M-A | M-B |
| **M-D** | сьюта `selfcheck_early` + расширения `nudge`/`skip`/`reconvert`/`reliability`; гейт 21→22; живой тест | M-A..C | — |
| **M-E** | **починка `_files_are_stable`** (перечитывать каталог, а не сравнивать готовый список) — существующий баг | — | любым |

## 3. Инварианты (без способа проверки не считается)

| # | инвариант | чем проверяется |
|---|---|---|
| I1 | Сборка по неполному манифесту **невозможна** | `build_token` отсутствует физически; сьюта: команда, рождённая по скелету, отвергается И ПОСЛЕ финализации (TOCTOU-кейс #2) |
| I2 | Один нудж на публикацию | `confirm_token` чеканится один раз на скелете; сьюта `nudge` + **новый кейс: приложение не поднимает окно вторым каналом** |
| I3 | Окно не открывается на копирующейся книге | дебаунс перед нуджем + M-E; сьюта: файл, доехавший после составления списка, ловится |
| I4 | Скелет не замерзает | замыкание по rev пропускает только `ready`/терминальные; resume с сохранением token; сьюта: halt после фазы → следующий тик достраивает |
| I5 | Пропущенная книга не воскресает | ранняя ветка сверяет `source_rev` (только `stat`) до записи скелета; сьюта `skip` |
| I6 | Сетевой сбой не выглядит проблемой доступа | таймаут веба не влияет на `folder_access`; сьюта `access` |
| I7 | Порядок публикации | манифест → state → леджер → нудж; порядковые проверки по журналу |
| I8 | Старые манифесты читаются | отсутствие поля фазы = `done` |

## 4. Вопросы человеку

Вопрос Sol'а «ждать ли кнопке веб-поиск обложки» **снят основой #1** — веб уходит с критического
пути, ждать нечего. Остаются два, оба про то, что человек ВИДИТ:

1. **Список глав в первую секунду.** Показать сразу имена файлов (рекомендую) — тогда окно
   осмысленно с первого кадра, но при чтении тегов возможен разовый пересорт, если в ID3 номера
   треков идут не как в именах файлов. Альтернатива — серые полосы-заглушки до чтения.
2. **Порядок ленты обложек.** Сделать её append-only: сначала из файла, потом сгенерированные,
   потом найденные в сети — чтобы поздние находки не сдвигали плитки под курсором.

## 5. Чего осознанно НЕ делаем

- не трогаем дебаунс 0.5 с (семантика E10, а не жир);
- не заводим отдельный канал «окно реально показано» (решение D16: видимость знает приложение);
- не переписываем лестницу показа окна (`app/WindowPresentation.swift` — свежий отревьюенный фикс);
- fsync родительского каталога в `write_json_atomic` и транзакционность «манифест+состояние» —
  зафиксированы как известные, но **после 1.0**: они не привнесены D17 и не блокируют его.
