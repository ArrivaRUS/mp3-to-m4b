# test-plan.md — mp3-to-m4b (гейты валидации)

> Что проверяем на каждом милстоуне до перехода дальше. Источники сценариев: PRD §8 (Given-When-Then),
> §9 (edge E1–E18), `research/m4b-toolchain.md` (движок), `arch/synthesis.md` (риски). **Дата:** 2026-06-28.

## §M0 — Протокол (fake-engine), РИСК №1
Тесты (Tester unit/integration + Юрка прогон):
- **I2:** нет файла-команды в `queue/commands/` → книга НИКОГДА не уходит в `converting` (нет сборки).
- **Stale-rev:** команда с устаревшим `source_rev` (файлы книги изменились) → `confirm_rejected_stale`, без сборки.
- **Идемпотентность дубля:** две команды с одним `idempotency_key`/двойной клик → ровно один build.
- **Malformed:** битый JSON в `queue/commands/` → уезжает в `commands/bad/`, агент не падает, сборки нет.
- **Прерванное `converting`:** рестарт агента без живого pid → `error: interrupted` + temp вычищены.
- **Rising-edge:** появление `pending-confirm` поднимает окно (закрытое — открывается).
- **I1:** исходные файлы не меняются/не удаляются. **G5:** свежий выход → повторно не пересобирать.
- **Один писатель:** в коде приложения НЕТ записи в `state.json`/`queue/books/*` (ревью-проверка).

## §M0.5 — Разведка
- Теги полные → автор←artist/album, название←album, порядок←track, имена глав←title.
- Теги пустые, папка «Толстой - Война и мир» → парс автор/название; имена глав из имён файлов.
- Натуральная сортировка `01,02,…,10` (не `1,10,2`). Кириллица не ломается.
- Детект встроенной обложки (APIC) → превью из первого файла с ней.

## §M1 — Движок и вертикаль (по research)
- N mp3 (разные SR/каналы) → один `.m4b`, brand `M4A`, faststart; длительность = сумма **без дрейфа** (concat+aformat).
- `ffprobe -show_chapters`: N глав, верные START/END (1/1000), кириллические имена, fallback-имена.
- Обложка attached_pic (mjpeg) присутствует; исходники целы (I1); атомарность (нет полу-`.m4b` при сбое/отмене).
- **Цепочка обложки:** из mp3 / нет→веб (квадрат-кандидаты) / нет сети→генерация Pillow (квадрат, кириллица ок, не tofu) / ручная замена. Пустых обложек нет (G4-цель PRD).
- **Нарезка** (P1): части по границам глав, каждая валидна, своя обложка, `track=N/M`, `-map_chapters 1` (нет дублей/фантомных глав); порог<главы → часть=глава + предупреждение.

## §M1 — Edge-cases (E1–E18 PRD §9)
Нет тегов · разные SR/каналы · битый mp3 (warn «без него») · нет интернета (→генерация) · нет места
(danger, cleanup) · повторная конвертация (идемпотентность) · отмена в процессе · очень длинная книга
(лимит дескрипторов→fallback demuxer) · мусор в папке · недокопированный mp3 · недопустимые символы в
имени · один mp3 в подпапке · дубли имён глав · размонтирование · порог<главы · краш при сборке (cleanup).

## §Показ окна — «окно создано» ≠ человек его видит (`.patches/006`, 2026-07-27)
Юнит: `app/selfcheck_routing.swift` → `python3 -m agent.selfcheck_app_routing` (входит в `selfcheck_all`).
Проверяется ЧИСТОЕ правило лестницы `WindowPresentation` — вызовы AppKit юнитом не проверяются.
- **Полная матрица** `next(after:isActive:isVisible:)`: 4 ступени × 4 комбинации фактов = **16 случаев**,
  ожидание задано явно для каждого; мета-проверка следит, что таблица не потеряла и не задвоила строку.
- **Короткое замыкание:** `isActive || isVisible` → `satisfied` на ЛЮБОЙ ступени, включая терминальную
  `.done` (поздний тик у уже видимого окна не имеет права дёрнуть док).
- **Монотонность:** эскалация не идёт назад и не перепрыгивает ступень
  (`ordered → orderedRegardless → attentionRequested → done`). Ранги ступеней — независимая фикстура
  в сьюте, а НЕ выведены из проверяемого правила.
- **Идемпотентный терминал:** из `.done` при невидимом окне → `escalate(.done)`; 10 повторных входов
  ничего не меняют; таймер не заводится.
- **`recheckDelay`:** `nil` РОВНО для `.attentionRequested` и `.done`; для остальных — конечная
  положительная пауза, сверяемая с **константами** (`recheckAfterOrdered` / `…Regardless`), а не с
  литералами 1.0/1.5 — подстройка паузы не должна ломать тест. Перекрёстный инвариант двух функций:
  таймер заводится ⇔ следующая ступень действительно что-то делает.
- **Отсутствие цикла:** невидимое окно от `.ordered` доходит до `.done` за 3 шага и остаётся там;
  сторож на 16 итераций превращает зацикливание правила в красный тест, а не в зависшую сьюту.
- **Связь с хостом** (структурно, чтением `app/main.swift` — как `checkRefitWiring`; `checkPresentationWiring`).
  Утверждения идут по **телам функций**, а не по файлу, и по исходнику **без строк-комментариев**:
  «слово встречается в main.swift» зеленеет от вызова на мёртвой ветке и от упоминания в прозе —
  `orderFrontRegardless` лежит в файле трижды, дважды в комментариях, а `NSApp.unhide` — только в них.
  - решателю дают `NSApp.isActive` + `occlusionState.contains(.visible)`; таймер — из `recheckDelay`;
    ступени — `orderFrontRegardless()` и РАЗОВЫЙ `.informationalRequest` (никогда `.criticalRequest`);
  - **лестница — единственный способ поднять окно:** все `makeKeyAndOrderFront` / `orderFrontRegardless` /
    `.activate` / `orderFront` / `deminiaturize` в хосте посчитаны и обязаны лежать внутри
    `presentWindow` / `performPresentationStep` / `activateApp`. Образцы БЕЗ получателя — иначе сторож
    обходится через `window?.` (замерено: первая редакция пропустила такой мутант, 317/317 зелёных);
  - **и в неё заходят:** все 5 путей показа (`applicationDidFinishLaunching`,
    `applicationShouldHandleReopen`, `refreshNow` — фронт «пришла новая книга», `handleInstalled`,
    `requestConsentNotice`) зовут `presentWindow()`. Зеркало предыдущего пункта: тот ловит подъём мимо
    лестницы, этот — пропавший показ (мимо никто не поднимает, просто показывать перестали);
  - **наблюдатель окклюзии** зарегистрирован в `installFocusObservers` и гасит лестницу по
    ПОЛОЖИТЕЛЬНОМУ признаку (`occlusionState.contains(.visible)` → `endPresentationEscalation()`);
    обработчики режутся поштучно, иначе утверждение собирает вызов из соседнего;
  - **порядок несущий:** `installFocusObservers()` строго ДО `presentWindow()` в
    `applicationDidFinishLaunching` — уведомление без слушателя не доставляется никому;
  - **вторая книга в живое приложение:** `applicationShouldHandleReopen` ведёт в `presentWindow()`
    и не поднимает окно мимо лестницы;
  - **раз-прятывание:** `NSApp.isHidden` → `unhideWithoutActivation()`, никогда plain `unhide(`;
  - **монотонность повторного входа:** `presentWindow` при `presentationCheck != nil` повторяет
    ТЕКУЩУЮ ступень; сброс на базовую — ровно один, в ветке нового прогона, после отзыва подскока;
  - **закрытое окно:** `guard window.isVisible` стоит строго ДО решателя;
  - **отзыв запроса внимания:** `cancelUserAttentionRequest` ровно в одном месте, идемпотентен,
    и путь ВЫХОДА ведёт в него целиком (`applicationWillTerminate` → `endPresentationEscalation` →
    `withdrawAttentionRequest`), а лестница гаснет ДО снятия наблюдателей.
  Инструмент грубый: доказывает, что связь ЕСТЬ и стоит в нужном месте, а не что она срабатывает.
- **Мутационная проверка** (разово, вне репо; правило — 2026-07-27, проводка — 2026-07-27):
  6 дефектов правила — все красные (перепрыгнутая ступень, шаг назад, `||`→`&&`, лишний таймер,
  зацикленный терминал, вырезанный вызов правила в хосте); 2 безобидные подстройки констант — зелёные.
  По проводке: **15 сломанных проводов — все красные**, **2 контроля зелёные** (переименование локальной
  переменной наблюдателя; дописанная в комментарий цитата вызовов лестницы). Ловится в том числе
  подъём окна мимо лестницы через `window?.`, `orderFront(` и `deminiaturize(`, и обратное —
  выпавший `presentWindow()` из фронта новой книги и из передачи после установки.
- **Принципиально НЕ покрыто юнитом:** поведение AppKit/WindowServer — даст ли `orderFrontRegardless()`
  видимость на конкретном Space/дисплее и что решит кооперативная активация Tahoe. Только живой прогон
  человеком (гарантированный ФОКУС без его действия недостижим — `.patches/006`, правило 4).
- **НЕ покрыто и структурно** (честные дыры сторожей, не забыть при следующем касании):
  - *условие* фронта: сторож видит, что `refreshNow` зовёт `presentWindow()`, но не то, что условие
    «появилась НОВАЯ книга» посчитано верно. Сломанный `newPending` не покраснеет здесь — он
    ловится значениями в сьютах `queue` / `nudge`;
  - *принадлежность ветке:* «повторный вход повторяет текущую ступень» доказано наличием ветки
    `presentationCheck != nil`, но что `withdrawAttentionRequest()` + `enterPresentationStep(.ordered)`
    лежат именно в `else`, текстом не доказывается (проверяется только их порядок и единственность);
  - *адресность наблюдателей:* `object: window` (наблюдаем СВОЁ окно, а не любое) не проверяется;
  - *факт срабатывания:* таймер `asyncAfter`, реальные переходы `presentationStep` и гонка с
    `applicationShouldTerminateAfterLastWindowClosed` — только живой прогон.

## §Ранний нудж (D17) — девять инвариантов, 2026-07-28
Окно поднимается за ~0.8 с вместо ~12 с, потому что книга публикуется ДВАЖДЫ: скелет (главы по
именам файлов, автор/название из папки) → дозаполненный манифест. Плата за это — новый класс
ошибок: окно открыто на манифесте, который ещё дозаполняется. Источник инвариантов —
`arch/early-nudge-synthesis.md` §3.

**Где что лежит.** Агент: `agent/selfcheck_early.py` (**93 проверки**, в гейте `selfcheck_all`,
всего сьют **22**) + новые кейсы в `nudge` (41→48), `skip` (26→32), `reconvert` (34→38),
`reliability` (16→18, кейсы E17/E18). Приложение: `agent/selfcheck_app_routing.py` (320→**423**) —
две ступени в одной сьюте: правила **значением** (`app/selfcheck_routing.swift`) и **проводом**
(`app/selfcheck_wire.swift`: команду пишет настоящий `EngineClient`, судит настоящий
`dispatcher.validate_command`).

| # | инвариант | чем проверяется |
|---|---|---|
| I1 | сборка по неполному манифесту невозможна | **TOCTOU:** команда, рождённая по скелету, отвергается И ПОСЛЕ финализации того же `source_rev` с тем же `confirm_token` — по несовпадению `build_token` (его у скелета нет ФИЗИЧЕСКИ). Fail-closed: токена нет / подделан / null / главы структурно пусты → `VERDICT_REJECT_NOT_READY` + `confirm_rejected_not_ready`, книга остаётся `pending-confirm`. Тот же кейс сквозь настоящий провод приложения |
| I2 | один нудж на публикацию | `confirm_token` чеканится ОДИН раз (на скелете) ⇒ ключ леджера у скелета и у ready совпадает; две публикации = один подъём окна. **Второй канал** приложения считает новизну ТОЙ ЖЕ функцией: форма `NudgeEdge.bookKey` выводится из исходника Swift и сверяется с ключом агента (было — комментарий «byte-for-byte mirror») |
| I3 | окно не открывается на копирующейся книге | дебаунс стоит ПЕРЕД скелетом; файл, доехавший ПОСЛЕ составления списка, ловится перечитыванием каталога (M-E). В сьюте — со **встроенным негативным контролем**: старое сравнение (список сам с собой) на той же фикстуре зовёт растущую книгу стабильной |
| I4 | скелет не замерзает | halt после `skeleton` и после `chapters` (шов `MP3TOM4B_HALT_AFTER_PHASE`) → следующий тик достраивает, сохранив `confirm_token`/`source_rev`, без второго нуджа. Структурно: замыкание по неизменившемуся rev фазозависимо (полный манифест → возврат как есть, неполный → resume) |
| I5 | пропущенная книга не воскресает | ни готовая, ни скелет: статус в условии замыкания — несущий, пропущенному скелету НЕ выдаётся `build_token` |
| I6 | сетевой сбой ≠ проблема доступа | мёртвая сеть: `exit 0`, `folder_access` = `ok`, сторож фазы молчит. **Обязательный негативный контроль** (дочерний процесс — сторож уходит через `os._exit`): тот же тик с веб-ногой, возвращённой внутрь `_finish_manifest`, даёт `exit 75` + `folder_access='blocked'` |
| I7 | порядок публикации | манифест → `state.json` → леджер → нудж, по журналу вызовов |
| I8 | старые манифесты читаются | отсутствие поля фазы = `done`; до-D17 манифест поднимается на месте (`manifest_phase_upgraded`) без нуджа и ре-арма; скелету и готовой книге токен НЕ выдаётся |
| I9 | лента обложек append-only | список до веба — ПРЕФИКС списка после; id/имена показанных плиток и `cover_selected` не меняются; ревизия книги не тронута; поздний воркер ПРОШЛОГО поколения отбрасывается; бюджет прохода и очередь команд уступают человеку |

**§0 — сам критический путь, СТРУКТУРНО, а не секундомером.** Замеры M-A/M-B (0.52 с до нуджа;

## §Сторож blast_radius — «сьюта не дотянулась до системы человека» (`.patches/005`)
**Один механизм на всех.** Вердикт даёт ТОЛЬКО общий сторож `agent/selfcheck_blast_radius.py`
(`snapshot()` / `diff()`): его берёт раннер `selfcheck_all` вокруг каждой сьюты, и он же — источник
вердикта внутри `selfcheck_installer_repoint` (с 2026-07-27; до этого сьюта держала СВОЮ копию,
сравнивавшую mtime боевого лога дословно). Второй копии этой логики в репо быть не должно.
- **Почему дословное сравнение mtime не годится.** У человека работает боевой агент: `StartInterval=300`,
  `StandardOutPath` = `~/Library/Logs/mp3-to-m4b.log`. Лог сдвигается сам раз в 300 с; сьюта
  `installer_repoint` идёт ~20 с ⇒ ~7 % прогонов краснели на ровном месте (ловили живьём: гейт 20/21,
  сьюта 91/92, тот же код следом — 92/92). Это флак на релизном пути: сьюты едут внутри бандла.
- **Как отличается автор записи.** launchd на КАЖДОМ своём запуске печатает в `StandardOutPath` баннер
  `mp3-to-m4b agent alive`. Stdout дочернего процесса сьюты уходит в трубу раннера и в боевой лог
  попасть не может — эта асимметрия и отвечает на вопрос «тикнул агент или писал тест». Сверх баннера
  проверяется СОДЕРЖИМОЕ: пути внутри установки, `install_generation` из plist-env (тест его не подделает),
  append-only журнала, `agent_started` не больше числа баннеров.
- **Fail-closed, не «игнорируем лог».** Структурные факты (plist и его `ProgramArguments[0]`, байты
  helper/`runner.sh`, receipt, набор загруженных launchd-job, наличие дерева и watch-папки) строгие
  ВСЕГДА. Рантайм-факты меняются, только если изменение атрибутировано живому агенту. Нет живой
